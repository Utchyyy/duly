# Duly build rules

## Product
Duly is an enterprise-first vendor-management platform: an Enterprise governs how its cleaning Vendors deliver, each Vendor runs the operations that deliver value to Clients, and every clean becomes one record the Enterprise and Client can see. The buyer marketplace and the WFX labour exchange are deferred, not removed: they sit behind feature switches (see Enterprise below). Surfaces: Duly Enterprise `/enterprise`, Client site view `/client`, Duly Pro vendor console `/pro`, Duly Crew operative PWA `/crew`, Duly Admin `/admin`; the older buyer app `/` and Duly for Business `/business` remain for non-Enterprise buyers while the marketplace is open. WFX (workers, shifts, DBS, matching) is the labour layer underneath.

## Non-negotiables
- Ranking, matching, pricing and scoring are deterministic SQL functions (`rank_vendors`, `rank_candidates`, `price_quote`, `commute_band`). The frontend never re-sorts their output; AI never ranks or prices.
- AI output goes only to `approval_queue` as a draft for a human to approve.
- RLS on every table. No anon access. Signed-out visitors see marketing only.
- No hard-coded currency, tax, payment terms or check types: read `markets`, `segments`, `policies`.
- Payment release follows `policies`: first release (default 55%) on approval, or at month end for monthly plans; balance 48h after no complaint; platform fee deducted from the balance.
- Staff pay (`shifts.hourly_pay`) is visible only in Duly Pro and Admin.
- Every schema change is a migration in `supabase/migrations`. Never edit an applied migration; add a new one.
- Don't rewrite published git history. Never commit `.env`, exports or CSVs with personal data.

## Schema layout
- App tables live in `public` (exposed through the API, guarded by RLS).
- Access helpers (`is_member`, `has_org_role`, `can_see_job`, …) are SECURITY DEFINER functions in the `private` schema, which the API does not expose. Policies call them.
- The only callable RPCs are in `public`, and each checks access itself:
  - Matching and pricing: `rank_vendors`, `price_quote`, `rank_candidates`, `demand_by_town`, `corridor_suggestions`
  - Workflow: `create_buyer_org`, `submit_quote`, `decline_quote`, `accept_quote`, `schedule_visits`, `check_in`, `complete_job`, `approve_job`, `mark_payment_paid`
  - WFX shifts: `offer_shift`, `respond_to_shift` (WIIx score computed by trigger from the four ratings)
  - People: `add_member`, `org_member_emails`, `mark_notifications_read`
  - Email worker (service role only, never callable by people): `worker_claim_notification_emails`, `worker_finish_notification_email`
  - Enterprise and Client access: `enterprise_add_vendor` (Duly staff), `enterprise_set_vendor_status`, `enterprise_set_requirements`, `enterprise_review_claim`, `enterprise_vendor_compliance`, `enterprise_delivery_board`, `enterprise_vendor_delivery`, `enterprise_open_issues`, `enterprise_escalate_issue`, `enterprise_set_sla_targets`, `enterprise_sla_pack`, `enterprise_sla_exceptions`, `grant_site_access`, `revoke_site_access`, `site_access_list`, `can_judge_job`; Duly staff set up and switch: `admin_create_enterprise`, `admin_create_vendor`, `admin_set_feature`
  - Admin evidence: `admin_case_timeline` (platform admin only; merges `audit_log` with a job's own events)
  - AI drafts: `approve_brief_draft`, `reject_brief_draft` (the model's output sits in `approval_queue` until a person approves it)
- `audit_log` is an append-only record written by triggers (briefs and locked versions, quotes, contracts, jobs, assignments, photos, ticks, verdicts, issues, payments, verification claims, AI draft approvals). Only a platform admin reads it, it holds ids not foreign keys so it survives deletes, and a trigger refuses any change or removal. Admin → Case files shows it with the evidence for arbitration. New tables that carry a request or its outcome should get an `audit_row` trigger.
- Triggers guard what direct writes can't be trusted with: job status/value (`protect_job_fields`), verdicts (`protect_area_result_fields`), verification tier (`protect_org_fields`), evidence geofence, issue SLA and dispute holds.

## Workflow
Brief (draft → locked version) → client invites ranked vendors → vendor submits (price computed by `price_quote`) → client accepts with a start time (creates contract, job, escrow line for escrow segments) → vendor assigns crew → crew checks in (geofence checked in SQL), ticks standards, uploads after-photos to `evidence/<job_id>/<area_id>/…` → `complete_job` → client marks each standard met/not met → `approve_job` schedules releases from `policies`, or a reported issue holds the job as `disputed` → Duly records bank transfers with `mark_payment_paid` (Stripe to replace) → `recompute_vendor_score` from real jobs only (it reads `private.visit_metrics`, the same per-visit measures the vendor and Duly see: on time, right first time, areas ticked, complaint-free, plus client verdicts from standards and plan areas, repeat clients and verification; the weights are `policies.ranking_weights`, divided by the weights that apply). Client charges: escrow segments get an `escrow_hold` line per clean; monthly plans get a `direct_debit` line per month (due at the start of the month) and invoice-terms clients an `invoice` line (due month end + payment terms), both kept in step with booked visits by `refresh_client_charges`.

Work schedules: a vendor answers a brief with a work schedule (`work_schedules`, built in Pro from `work_plan_templates`): Section > Sub-section > Cleaning area, each set per weekday to scrub, wash, clean or mop, with the vendor's minutes for each method. It is for the work, not the price (`price_quote` is unchanged). The client sees it with the quote once the vendor sends it; accepting the quote locks it (a trigger, and the database owner cannot edit it after), crew see the weekday's work on their job sheet, and a complaint (`issues.plan_item_id`) can name the exact cleaning area, with its path worked out by the database. Shared templates are seeded from a gym operator's sample; vendors keep their own. On a job with a locked schedule that plans something for the visit's weekday (taken in the buyer's market timezone), the planned cleaning areas are the checklist instead of the brief's standards: the crew tick each one (`plan_results`) and take an after photo for every sub-section worked (`evidence.area_id` is the sub-section, optionally tagged with `plan_item_id`); `complete_job` and `approve_job` enforce it in SQL; the client accepts each area or reports a problem on it (which marks it not met until accepted again). One checklist: the work schedule is the checklist for every new job (`public.job_check_mode` tells the app which applies: `plan`, `photos` or `standards`). When the client accepts a quote the vendor sent no schedule for, Duly builds and locks one from the brief (`private.derive_work_schedule`: each brief area is a sub-section with the same id and a `brief_area_id` link, each standard a cleaning area `d1`, `d2`…, every day, method `clean`, the brief's minutes shared across them so planned time still matches the booking; an area with no standards is one cleaning area; an empty brief gets none). When the vendor sent one, each sub-section linked to a brief area also carries that area's standards, written into the locked plan as extra cleaning areas flagged `standard` (`private.plan_with_standards`) on the days the sub-section is worked: ticked, judged, complained about and measured like any area, adding no planned minutes (the schema check ignores their placeholder method). A weekday the schedule plans nothing is `photos`: no area checklist, the crew need at least one after photo and the client approves the visit as a whole or reports a problem on it. `standards` (the older ticked-and-judged brief standards in `area_results`) now serves only a job with no locked schedule at all, which is any job made before this or from an empty brief.

Rework visits: a complaint that names a cleaning area (quality, access, no-show or other; never safeguarding, damage or conduct) becomes a planned visit. The vendor books it (`book_rework`) as a job linked to the complaint (`jobs.rework_of_issue`): no contract, no price, no payment, and its checklist is that one area whatever the weekday (`private.job_planned_rows` and `job_weekday` handle it). The crew do it with the normal check-in, tick, photo and complete; the person who reported the problem accepts or rejects it (`review_rework`). Accepting resolves the complaint and marks the area met on the original visit so it can be approved and paid as normal; rejecting sends the complaint to Duly (`mediation`). A vendor cannot close a complaint against itself, and `approve_job` refuses a rework. Rework visits are left out of a vendor's own rates and score (`vendor_ops`, `vendor_visits`, `recompute_vendor_score`); `vendor_rework` reports on them. A complaint that names no area (reported on the visit as a whole), and any complaint on an older job with no schedule, has no rework visit.

Dispatch board: Pro → Dispatch (`dispatch_board`, `dispatch_crew`; vendor admin and dispatcher staff and Duly, never crew) lists every non-cancelled visit in a date range (plus any unfinished one from before it) with who is on it and what needs attention, all worked out in SQL with the same rules as the reminder scan (lateness tolerance from the brief, then the policy, then 15 minutes): `late`, `no_crew`, `crew_clash` (a cleaner on overlapping visits), `overrunning` (in progress past its planned end) and `held` (a complaint holds it). Rows that need attention come first, oldest first; the app keeps that order, counts the flags and groups the rest by day, and never re-sorts. No pay, price or client contact appears. Crew can be assigned and removed from the board with the same component as Jobs and crew (`AssignCrew`).

Enterprise: an Enterprise is a buyer organisation in the `enterprise` segment, and it is the buyer on the contract, so every buyer rule (brief, quote, contract, visits, judging, rework, measures) works for it and it sees everything its vendors do on its sites. The enterprise segment's payment model is `external` (invoicing is outside Duly): a quote carries no price, and accepting, approving and the charge refresh write no escrow, charge or release lines. Work starts by appointment, not by ranking: Duly staff put a vendor on the Enterprise's roster (`enterprise_vendors`, status `invited`), the Enterprise accepts it (`active`) or suspends it, and an Enterprise can only invite a roster vendor that is active and only accept a quote from one (`private.vendor_on_roster`); the vendor sends a work schedule and the Enterprise accepts it. Vendors verify to the Enterprise's own satisfaction (the enterprise segment's minimum tier is 0), not Duly's tier. A Client gets a login for a site (`site_access`, granted by the Enterprise's owner or approvers by email): a manager can judge the work like the Enterprise's staff (`private.is_job_buyer` includes site managers), a viewer only sees the record; neither sees money, quotes, contracts or the roster. The app asks `can_judge_job` to show the judging controls. Vendor evidence: the Enterprise verifies its own vendors' company claims (`enterprise_requirements` says which kinds it requires, never DBS or right to work, which are personal; `enterprise_review_claim` accepts or rejects one claim with a reason for a rejection; `enterprise_vendor_compliance` works out each roster vendor's state per required kind in SQL: `not_sent`, `awaiting`, `accepted`, `rejected`, `expired`). It sits beside Duly's own checks and does not replace them, and it gates nothing: the roster stays the gate. A vendor changing a claim's kind, reference or expiry clears the decisions on it (`private.clear_reviews_on_claim_change`). The vendor sees each Enterprise's decision and reason in Pro → Verification. Delivery view: Enterprise → Delivery (`enterprise_delivery_board`, `enterprise_vendor_delivery`, `enterprise_open_issues`; Enterprise members and Duly) shows every vendor's visits at its sites across a date range, worked out in SQL with the same lateness rules as the dispatch board: `missed` (nobody checked in and the planned end has passed), `late`, `no_crew` (starts within 24 hours with nobody assigned), `overrunning`, `held`, `awaiting_check`; most urgent first, and the app keeps that order. Each roster vendor gets a scorecard (visits evidenced = checked in, every planned area ticked and a photo; on time; late; missed; complaints; open problems; past response time; right first time) and open problems are listed past-response-time first. No pay, price or crew names appear and safeguarding reports are never shown. An owner or approver can hand an open problem to Duly with `enterprise_escalate_issue` (status `mediation`; never safeguarding or a resolved problem). Monthly SLA pack: Enterprise → Reports (`enterprise_sla_pack`, `enterprise_sla_exceptions`; Enterprise members and Duly) is one calendar month (the Enterprise's market timezone; visits scheduled in it, not cancelled, not rework) per vendor and per vendor and site, worked out in SQL with the delivery view's measures: visits scheduled and due, evidenced, on time, late, missed, average minutes after the start, planned areas ticked, right first time, complaints (per 100 due visits), open complaints, past response time. The exceptions list is every missed, late or complained-about visit behind the numbers. Service levels are the Enterprise's own and optional (`enterprise_sla_targets`: lowest on-time share, lowest evidenced share, most complaints per 100 visits; `enterprise_set_sla_targets`, owner or approver); with none set nothing is judged and the `met` columns are empty. The app only displays and exports (CSV written in the browser from the rows, every cell made safe against spreadsheet formulas, plus print to PDF); no crew names, pay or price, and safeguarding reports are never counted. The current month is a partial pack. Feature switches (`app_features`, set by Duly staff in Admin → Feature switches): `buyer_signup` is enforced in the database (`create_buyer_org` is refused for anyone but Duly staff when off); `marketplace` and `shifts` hide those screens; all default on, and Duly turns them off for the Enterprise launch. They fail closed in the app (unreadable means hidden). Reactivating a deferred feature is switching it back on.

AI drafting (optional): a buyer pastes text or uploads a document → a server function (`src/lib/drafting`, as the signed-in person) asks the model for a draft → a pending row in `approval_queue` → an owner or approver reviews it → `approve_brief_draft` creates the site and an unlocked draft brief (areas the drafter left without standards get up to 3 `standards_library` entries for the organisation's segment and the area type) → the person edits, locks and asks for quotes as usual. The schema has no price or vendor field, and limits (10 pending, 25 a day per organisation) are enforced by trigger. `ANTHROPIC_API_KEY` is server-only.

Notifications: created only in SQL (triggers on quotes, jobs, assignments, issues, shifts, DBS and verification, plus the scheduled `private.notify_due_items()`), into `notifications` (the in-app inbox, which doubles as the email outbox). They never carry staff pay, amounts, street addresses, access notes or safeguarding detail, they never block the action they report, and people can only read them and mark them read. Email is sent by `POST /api/notifications/send` (needs `CRON_SECRET`), which uses the service role; those secrets are server-only.

Crew offline: `public/crew-sw.js` (scope `/crew`) caches only the app's static files and the Crew page shell, never data, and never anything cross-origin or non-GET. Check-in, ticking and completing need a connection because the database records their time and place as "now". Photos taken without one are kept in IndexedDB (`src/lib/crew/outbox.ts`) with their original time and place and sent when the signal returns; `evidence.storage_path` is unique so a resend cannot duplicate. A failed load is never shown as "no jobs" or "no access" (`loadFailed` in `useAuth`).

## Auth
Email one-time code (Supabase OTP). Buyers and operatives can sign up; vendor staff and admins are invite-only (`shouldCreateUser: false`). Roles come from `memberships`.
